# Porting notes: tool

Resolves issue #11 (porting notes: tool).
The tool module is 38 files and 2,866 lines (DEPS).
It holds the stone-age tool items, the shears, the shields, the crude fishing rod,
and the tool repair kits. The two repair recipe classes move here from core.
This document lists each 1.12 construct and its 1.21 replacement.
Decisions that need Moos are collected at the end.

## Sources

- **1.12**: the `1.12` branch of this repo, package `com.codetaylor.mc.pyrotech.modules.tool`,
  plus the two repair recipe classes in `modules.core.recipe`.
- **ATHENAEUM**: the athenaeum library source on GitHub
  (`codetaylor/athenaeum`, `master`, `reference/ModuleMaterials.java` and `reference/EnumMaterial.java`).
  The 1.12 mod reads its bone and flint tool materials from there.
- **NF-SRC**: the decompiled NeoForge 21.1.249 sources this project compiles against, at
  `build/moddev/artifacts/neoforge-21.1.249-sources.jar`. Paths cited below are entries in that jar.
- **NF-DOCS**: docs.neoforged.net, 1.21.1 version pages. URLs cited inline.
- **CORE**: `docs/research/porting-notes-core.md` on branch `research/porting-notes-core`.
- **RECIPES**: `docs/research/recipe-architecture.md` on branch `research/recipe-architecture`.
- **DEPS**: `docs/research/module-dependencies.md` on branch `research/module-dependencies`.

## Summary

- The module registers 50 items. All of them become `DeferredItem` fields on one
  `DeferredRegister.Items` holder, following the core idioms.
- The five 1.12 tool materials plus the config maps flatten into eight `SimpleTier`
  constants. Numeric harvest levels become incorrect-for-drops block tags.
- The redstone and quartz "active tool" NBT hacks become two custom data components.
- The two repair recipe classes from core become one data-driven crafting recipe
  type, `pyrotech:tool_repair`, generated by datagen for the eight durable tools.
- The shield Java models and the TEISR renderer map one to one onto
  `LayerDefinition`, `BlockEntityWithoutLevelRenderer`, and `RegisterClientExtensionsEvent`.
- Almost all of `ModuleToolConfig` gets baked into registration-time constants.
  Tier values cannot stay runtime-configurable in 1.21 (see decision 1).

## Tool tier mapping

### The 1.12 inputs

1.12 has five `Item.ToolMaterial` sources and two config maps that override them:

- `EnumMaterial.BONE.getToolMaterial()`: level 1, 150 uses, speed 3.8, damage bonus 1.0, enchantability 5 (ATHENAEUM).
- `EnumMaterial.FLINT.getToolMaterial()`: identical numbers to bone (ATHENAEUM).
- `ModuleMaterials.OBSIDIAN`: level 2, 1400 uses, speed 6.0, damage bonus 2.0, enchantability 18 (ATHENAEUM).
- `ModuleCore.Materials.REDSTONE`: level 1, 200 uses, speed 2.8, damage bonus 1.0, enchantability 9 (1.12 `ModuleCore.java` line 649). Moves to tool per CORE.
- `ModuleCore.Materials.QUARTZ`: level 1, 350 uses, speed 3.2, damage bonus 1.0, enchantability 2 (1.12 `ModuleCore.java` line 650). Moves to tool per CORE.
- Crude tools use vanilla `ToolMaterial.STONE` and then halve the mining speed in a
  `getDestroySpeed` override.

The config maps in `ModuleToolConfig` override durability
(crude 32, bone 150, bone durable 600, flint 150, flint durable 600, redstone 200,
quartz 350, obsidian 1400) and harvest level (crude 0, obsidian 2, everything else 1).
The item base classes apply them with `setMaxDamage` and `setHarvestLevel`.

### The 1.21 shape

A tool material in 1.21.1 is the `Tier` interface. NeoForge's `SimpleTier` is the
plain implementation: incorrect-blocks tag, uses, speed, attack damage bonus,
enchantment value, repair ingredient supplier (NF-SRC
`net/neoforged/neoforge/common/SimpleTier.java`; NF-DOCS
https://docs.neoforged.net/docs/1.21.1/items/tools/). Tiers are not registry
objects. They are static constants in the tool package.

Two consequences shape the mapping:

- Numeric harvest levels are gone. Each tier names a block tag of blocks it
  cannot harvest. Level 0 maps to `BlockTags.INCORRECT_FOR_WOODEN_TOOL`, level 1
  to `INCORRECT_FOR_STONE_TOOL`, level 2 to `INCORRECT_FOR_IRON_TOOL`
  (NF-SRC `net/minecraft/world/item/Tiers.java`).
- `TieredItem` forces `properties.durability(tier.getUses())` in its constructor,
  and that call overwrites any durability set earlier (NF-SRC
  `net/minecraft/world/item/TieredItem.java` line 7, `Item.java` line 456).
  A per-item durability that differs from the tier is not possible. So every
  distinct durability needs its own tier, and the 1.12 config maps bake into the
  tier constants (decision 1).

### The eight tiers

The durable variants share stats with their base material except uses, so they
are separate tiers. The crude tier bakes the halved stone speed (4.0 times 0.5),
which deletes the `getDestroySpeed` overrides in the four crude tool classes.

| Tier | Incorrect tag | Uses | Speed | Damage bonus | Ench | Repair ingredient |
|---|---|---|---|---|---|---|
| CRUDE | `INCORRECT_FOR_WOODEN_TOOL` | 32 | 2.0 | 1.0 | 5 | cobblestone (vanilla stone material default in 1.12) |
| BONE | `INCORRECT_FOR_STONE_TOOL` | 150 | 3.8 | 1.0 | 5 | `minecraft:bone` |
| BONE_DURABLE | `INCORRECT_FOR_STONE_TOOL` | 600 | 3.8 | 1.0 | 5 | `minecraft:bone` |
| FLINT | `INCORRECT_FOR_STONE_TOOL` | 150 | 3.8 | 1.0 | 5 | `minecraft:flint` |
| FLINT_DURABLE | `INCORRECT_FOR_STONE_TOOL` | 600 | 3.8 | 1.0 | 5 | `minecraft:flint` |
| REDSTONE | `INCORRECT_FOR_STONE_TOOL` | 200 | 2.8 | 1.0 | 9 | `pyrotech:dense_redstone` |
| QUARTZ | `INCORRECT_FOR_STONE_TOOL` | 350 | 3.2 | 1.0 | 2 | `pyrotech:dense_quartz` |
| OBSIDIAN | `INCORRECT_FOR_IRON_TOOL` | 1400 | 6.0 | 2.0 | 18 | empty (1.12 set no repair item) |

The redstone and quartz repair ingredients replace the 1.12 `getIsRepairable`
overrides on those ten items. `TieredItem.isValidRepairItem` already tests the
tier's repair ingredient (NF-SRC `TieredItem.java` line 24).

### Attack attributes

1.12 attack damage and speed sat in vanilla per-material arrays plus explicit
constructor arguments. 1.21 moves them to `ItemAttributeModifiers` built with the
static `createAttributes(Tier, attackDamage, attackSpeed)` on each tool class.
The final modifier is the damage argument plus the tier's bonus (NF-SRC
`net/minecraft/world/item/DiggerItem.java` line 18, `SwordItem.java` line 42).
So the 1.21 damage argument is the 1.12 total minus the tier bonus:

| Tool type | 1.12 numbers | 1.21 `createAttributes` args |
|---|---|---|
| Axes (crude, bone, flint) | total 8.0, speed -3.2 | `(tier, 7.0F, -3.2F)` |
| Axe (obsidian) | total 8.0, speed -3.0, bonus 2.0 | `(tier, 6.0F, -3.0F)` |
| Axes (redstone, quartz) | total 8.0, speed -2.8 | `(tier, 7.0F, -2.8F)` |
| Pickaxes | vanilla shape | `(tier, 1.0F, -2.8F)` |
| Shovels | vanilla shape | `(tier, 1.5F, -3.0F)` |
| Swords | vanilla shape | `(tier, 3.0F, -2.4F)` |
| Hoes (bonus 1.0 tiers) | modifier 0, speed -2.0 | `(tier, -1.0F, -2.0F)` |
| Hoe (obsidian, bonus 2.0) | modifier 0, speed -1.0 | `(tier, -2.0F, -1.0F)` |

## The redstone and quartz active system

Ten items (five redstone, five quartz) share an activation mechanic. The 1.12
implementation is NBT under a `Pyrotech` compound, two marker interfaces
(`IRedstoneTool`, `IQuartzTool`), and two static delegates.

| 1.12 construct | 1.21 replacement |
|---|---|
| `Pyrotech.RedstoneToolActiveExpiresTimestamp` (long, wall-clock millis) and `Pyrotech.QuartzToolActive` (boolean) NBT keys | Two custom data components registered with `DeferredRegister.createDataComponents()`: an expiry value for redstone and a boolean for quartz. Both need `persistent` and `networkSynchronized` codecs (NF-DOCS https://docs.neoforged.net/docs/1.21.1/items/datacomponents/). See decision 3 for the clock. |
| `IRedstoneTool`, `IQuartzTool`, `RedstoneToolDelegate`, `QuartzToolDelegate` | Keep the shape: two small interfaces plus two delegate classes reading the data components. The delegates shrink because component access is one call. |
| `setDamage` override chain (chance to skip damage while active, chance to activate on damage) | `IItemExtension#setDamage(ItemStack, int)` still exists as an overridable hook (NF-SRC `net/neoforged/neoforge/common/extensions/IItemExtension.java` line 399). The override ports directly. |
| `getDestroySpeed` scaling while active (3x quartz, 2x redstone) | `Item#getDestroySpeed(ItemStack, BlockState)` is still the hook (NF-SRC `Item.java` line 157). `ItemStack.getDestroySpeed` calls it, and the default reads the `Tool` component. The override multiplies the super result while active. The 1.12 field-swap trick on `efficiency` is not needed. |
| `getAttackDamage` override on the swords (damage scalar while active) | Attributes are a data component now. Swap `DataComponents.ATTRIBUTE_MODIFIERS` on the stack when the active state toggles, writing the scaled and unscaled `createAttributes` results. |
| `addPropertyOverride(new ResourceLocation("pyrotech", "active"), ...)` in constructors | `ItemProperties.register(item, ResourceLocation, fn)` for all ten items, called in `FMLClientSetupEvent#enqueueWork` (NF-SRC `net/minecraft/client/renderer/item/ItemProperties.java` line 60). The predicate id stays `pyrotech:active` so the 1.12 model override JSON keeps working. The `_active` textures are already migrated on `main`. |
| `RedstoneToolDelegate.activateNearbyDenseRedstoneOre` (per-tick cube scan, athenaeum `BlockHelper`) | Same logic in `inventoryTick`, iterating with `BlockPos.betweenClosed`. It touches core's dense redstone ore blocks and the six activation sounds, both registered in core per CORE. |
| `QuartzToolDelegate.onUpdate` (`world.provider.isNether()`) | `level.dimension() == Level.NETHER` in `inventoryTick`. |

## Repair recipes (moved from core)

### What 1.12 does

`BoneToolRepairRecipe` and `FlintToolRepairRecipe` live in `modules.core.recipe`
and extend `ShapelessOreRecipe` with a custom factory in `_factories.json`.
CORE assigns both to the tool module. Eight recipe JSONs use them, one per
durable tool (`bone_axe_durable_repair.json` and friends, in
`assets/pyrotech/recipes/tool/`). The shape:

- Ingredients: any `toolHammer` ore-dict hammer, the matching repair kit at any
  damage, the durable tool at any damage.
- Result: a copy of the tool with damage reduced by 25 percent of max durability
  (`PERCENTAGE_DURABILITY_REPAIRED`, config). An undamaged tool yields an empty
  result, so the craft is blocked.
- Remaining items: the hammer takes 4 damage (`HAMMER_REPAIR_DAMAGE`, config),
  the kit takes 1 damage (4 uses per kit). Either breaks and vanishes when it
  runs out.

### The 1.21 shape

One recipe class replaces both, following the RECIPES conventions:

- `ToolRepairRecipe implements CraftingRecipe`, with fields
  `Ingredient kit`, `Ingredient tool`, `float repairFraction`. One serializer
  `pyrotech:tool_repair` with a `MapCodec` and a `StreamCodec`, registered on the
  existing `PyrotechRecipeSerializers` register. No new `RecipeType`; crafting
  recipes use `RecipeType.CRAFTING` (NF-SRC
  `net/minecraft/world/item/crafting/CraftingRecipe.java`).
- `matches(CraftingInput, Level)` wants exactly three stacks: one in the
  `#pyrotech:hammers` tag, one kit match, one tool match with damage above zero.
  The damage check moves from `assemble` into `matches`, which is cleaner than
  the 1.12 empty-result trick.
- `assemble` returns the tool copy with
  `damage - (int) (maxDamage * repairFraction)`, clamped at zero, written through
  `DataComponents.DAMAGE`.
- `getRemainingItems(CraftingInput)` is overridable on `Recipe` (NF-SRC
  `net/minecraft/world/item/crafting/Recipe.java` line 33). It damages the hammer
  by 4 and the kit by 1, shrinking a stack that reaches max damage. This override
  replaces the default `getCraftingRemainingItem` path, so the hammer's own
  crafting-damage override from CORE does not double-fire here.
- `isSpecial()` returns true, matching the 1.12 `isSimple = false` intent.
- Datagen emits the eight JSONs under `pyrotech:tool_repair/<tool>` from a small
  loop in the tool recipe method of the `RecipeProvider`.

The kit and hammer damage amounts, the repair fraction, and the kit uses were
config in 1.12. They bake into the recipe JSON and item constants (decision 2).
The `#pyrotech:hammers` item tag replaces the `toolHammer` ore dict entry and is
written by the datagen `ItemTagsProvider`; core's hammers join it when core lands.

### The other module recipes

- The module ships 57 recipe JSONs in `assets/pyrotech/recipes/tool/`. Eight are
  the repair recipes above. The other 49 are plain shaped and shapeless recipes
  that regenerate through datagen into `data/pyrotech/recipe/`. Metadata ingredients
  (`pyrotech:material` data N) become the flat core items (`pyrotech:flint_shard`,
  `pyrotech:bone_shard`, `pyrotech:stick_stone`, `pyrotech:leather_cord`,
  `pyrotech:plant_fibers`). Ore-dict ingredients become tags per CORE
  (`rock` and `stickStone` become pyrotech tags, `stickWood` becomes `c:rods/wooden`).
- The repair kit recipes are plain shapeless: three shards (bone or flint), one
  stone stick, one leather cord.
- The `modules_enabled` conditions on every JSON die with the module toggles (CORE).
- The clay shears smelting recipe (0.1 xp) comes back through the `RecipeProvider`.

## Config

`ModuleToolConfig` has no category that survives cleanly:

- The durability and harvest maps bake into the tiers (decision 1, forced).
- The shears, shield, fishing rod, and kit durabilities bake into `Item.Properties`.
- The redstone and quartz behavior tunables (activation chances, speed and damage
  scalars, proximity repair) become constants unless Moos wants a
  `ModConfigSpec` (decision 2).
- The repair percentages and hammer damage bake into recipe JSON (decision 2).

## Known asset gap

Same gap as CORE found for materials. The migrated assets on `main` carry all
tool textures (including the ten `_active` variants) and all lang keys, but no
item models for the 50 tool items. The 1.12 models sit under
`models/item/tool/` with the `tool/` prefix baked into 1.12 model registration.
The 1.21 models are flat (`models/item/crude_axe.json`), so the port generates
them fresh: `item/handheld` parent for tools, `item/generated` for shears and
kits, predicate overrides for the ten active-capable tools, and `builtin/entity`
display models for the two shields.

The shield render stack maps as:

| 1.12 construct | 1.21 replacement |
|---|---|
| `ModelCrudeShield`, `ModelDurableShield` (two-box `ModelBase` Java models) | One `Model` class with a `LayerDefinition` per shield, registered in `EntityRenderersEvent.RegisterLayerDefinitions`. The vanilla `ShieldModel` is the pattern. |
| `TEISRShield` (`TileEntityItemStackRenderer`) | A `BlockEntityWithoutLevelRenderer` returned from `IClientItemExtensions#getCustomRenderer`, registered with `RegisterClientExtensionsEvent#registerItem` on the mod bus (NF-SRC `net/neoforged/neoforge/client/extensions/common/IClientItemExtensions.java` line 178, `RegisterClientExtensionsEvent.java` line 56). |
| Vanilla `blocking` model predicate (inherited from the vanilla shield) | `ItemProperties.register` for the two shields with the vanilla `blocking` logic. Vanilla registers that predicate only for its own shield item. |

The `textures/entity/crude_shield.png` and `durable_shield.png` files are already
migrated on `main`.

## Decisions for Moos

1. **Tier values are baked.** 1.12 exposed durability and harvest level as config
   maps. In 1.21 the tier constants own both, and `TieredItem` overwrites any
   per-item durability with the tier's value, so runtime config cannot drive them.
   Baking the 1.12 defaults is the only faithful option. Players tune mining
   levels through the incorrect-blocks tags in a datapack. Recommendation: accept
   the bake; this extends core decision 3 (drop value-tuning config).
2. **The remaining tool config knobs.** The redstone and quartz activation
   chances and scalars, the fishing rod break chance, and the repair kit numbers
   could survive as a small `ModConfigSpec`. Recommendation: bake the 1.12
   defaults as constants, consistent with core decision 3, and add config later
   only if someone asks.
3. **Redstone active timer clock.** 1.12 stores a wall-clock expiry
   (`System.currentTimeMillis`), so the buff drains in real time, even while
   paused, and the client and server clocks can disagree. Options: keep wall
   clock (byte-faithful), or store a game-time tick and compare against
   `Level.getGameTime()` (pause-safe, sync-safe). Recommendation: game time. The
   10-second feel is identical in normal play.
4. **Durability tooltips.** The "full durability" tooltip line on every tool sat
   behind `ModuleCoreConfig.CLIENT.SHOW_DURABILITY_TOOLTIPS`. Core decision 3
   drops that config category. Options: keep the tooltip unconditionally, or drop
   it. Recommendation: keep it unconditionally; it is quiet and informative.
5. **Repair recipe class shape.** One generic `pyrotech:tool_repair` serializer
   with the kit, tool, and fraction in JSON (recommended), or two hardcoded
   classes mirroring 1.12's `BoneToolRepairRecipe` and `FlintToolRepairRecipe`.
   The generic shape is one class, eight generated files, and covers any future
   kit. Recommendation: the generic serializer.
